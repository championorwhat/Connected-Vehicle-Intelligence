# ADR-005: Stream processing with Python consumer groups; canonical events as versioned JSON

**Status:** Accepted (M4), decided with measurements, as planned in M0.

## Context
M0 flagged the biggest technical risk: can Python normalise 100K events/s? M0 also planned
Protobuf for the canonical topic.

## Options considered
| Option | For | Against |
|---|---|---|
| **Python consumer group** (confluent-kafka + orjson) | One language across simulator, processor, API and ML; tiny footprint; scales by adding processes up to the partition count | Per-core throughput is lower than on the JVM |
| Kafka Streams (Java) | Best fit for keyed state and changelogs | Second language; JVM per instance on an 8 GB laptop |
| Flink | Event-time windows, exactly-once sinks | Cluster to operate; heavy locally |
| Faust / Bytewax | Pythonic streaming | Maintenance risk |

## Measurements (4 vCPU Linux container shared with Kafka, not the target Mac)
| Step | Result |
|---|---|
| First version, pure processing | 33 µs/event (30K/s per process) |
| After profiling-led optimisation: exact-type numeric checks, no re-rounding, BLAKE2b ids instead of uuid5, cached timestamp prefixes, cached VIN validity | **16–19 µs/event** (53–63K/s per process) |
| On Kafka, 1 process | **25.8K msg/s** (was 17.5K) |
| On Kafka, 3 processes in one group | **62.9K msg/s** (was 43.7K) |

Evidence: `evidence/benchmarks/m4-normalizer-*.json`.

## Decision
- Keep Python. Scale horizontally with processes in the `normalizer` consumer group.
  100K msg/s needs about 4–5 processes on dedicated cores. That is a deployment sizing
  question (M14/M16), not a redesign. A Go rewrite of the hot path remains the fallback if
  M14 shows otherwise.
- **Canonical format changed from Protobuf to versioned JSON** (`schema_version`, JSON Schema in
  `packages/schemas`, validated by contract tests). Reason: ClickHouse's Kafka engine reads
  JSONEachRow directly (M6), with no custom sink service and no schema registry. Cost: larger
  messages than Protobuf. Revisit if broker bandwidth becomes the bottleneck.

## Consequences
- At-least-once delivery: offsets are committed only after every output is acknowledged.
  Downstream idempotency relies on the deterministic `event_id`.
- The dedup state is per-partition and in memory. A rebalance can let one redelivered batch
  through, which the idempotent sinks absorb.
