# ADR-004: Consistency per data class (CAP / PACELC)

**Status:** Accepted (M6).

## Context
Different data has different costs of being wrong versus being late. A lost alert or a
double-counted work order is expensive. A telemetry point that is a second stale is not.

## Decision
| Data | Store | CAP under partition | PACELC else | Why |
|---|---|---|---|---|
| Raw and canonical telemetry | Kafka (`acks=all`, `min.insync.replicas=2` in the HA overlay) | **C**: refuse writes below ISR | EL: batched `linger.ms` | Losing telemetry hides faults. Producers buffer and back off rather than drop |
| Telemetry history | ClickHouse (async replicas) | **A** | **L** | Analytical reads tolerate seconds of lag; replays collapse by key |
| Alerts, work orders, tenants, RBAC, audit | PostgreSQL (single primary, synchronous commit) | **C** | **C** | State machines and money: correctness over availability |
| Live vehicle state, rankings, pub/sub | Redis | **A** | **L** | Rebuildable from `vehicle.state` (compacted) at any time |
| Detector and dedup state | Process memory, per partition | n/a | **L** | Rebuilt after rebalance; sinks are idempotent on deterministic ids |

## Consequences
- Delivery end to end is **at-least-once**. Every sink is idempotent on a deterministic key:
  `event_id` for events, `fingerprint` for alerts, `vehicle_id` for state. We do not claim
  exactly-once.
- During a PostgreSQL outage the sink retries with exponential backoff and jitter, then exits
  without committing offsets. Alerts are delayed, never lost. During a Redis outage the live
  view goes stale, not wrong.
- The no-data-loss claim is verified by `scripts/reconcile.py`, which is gated in CI.
