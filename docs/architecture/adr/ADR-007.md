# ADR-007: Accept LightGBM failure-7d-v1 over the rules; serve it through a shared feature path

**Status:** Accepted (M8).

## Context
ADR-006 said the ML model replaces the calibrated rules only if it beats them on held-out
data. M8 trained LightGBM on two simulated runs and tested it on three unseen runs: one
held-out run and two shifted variants ([model card](../../ml/model-card.md)).

## Decision
1. **Accept the model as the better risk source.** On every test set its PR-AUC is higher
   than the rules', and the 95% bootstrap interval of the gain excludes zero (held-out
   +0.23 [0.17, 0.30]). It also has a better Brier score and a better precision at workshop
   capacity.
2. **Training and serving use one feature implementation.** The live scorer will call the
   same `features.build` SQL, not a re-implementation. Silent training/serving skew is the
   most common way such a gain disappears in production.
3. **Until the scorer exists, the planner stays on the rules** (no half-wired path). Work
   orders already record `model_version`, so the switch will be visible, and it can be
   rolled back per proposal.
4. **Versioned, verified artefacts.** A model directory holds `model.txt` and
   `metadata.json` (feature list, category codes, parameters, SHA-256). Loading refuses a
   mismatch. A new version is a new directory, never an overwrite.

## Options considered
| Option | For | Against |
|---|---|---|
| **LightGBM (chosen)** | Strong on tabular data; µs inference; exact TreeSHAP explanations; small artefact | Needs engineered window features |
| Logistic regression | Simplest, fully transparent | Cannot model thresholds or interactions without hand-made features |
| Sequence model (LSTM/Transformer) on raw telemetry | No feature engineering | More data than justified, slower, harder to explain; M0 ruled it out |
| Keep only the rules | Nothing new to run | Measurably worse on held-out data |

## Consequences
- The advantage is measured in the simulator only; field performance is **NOT YET MEASURED**.
- Serving the model needs recent per-vehicle features from ClickHouse. This is scheduled
  with the API in M9, and verified by a parity test against the training features.
