# ADR-002: ClickHouse for telemetry and analytics

**Status:** Accepted (M0), implemented in M2 (schema) and M6 (Kafka ingestion).

## Context
About 8.6 B events/day at 100K ev/s. Queries are time-window scans per vehicle or tenant, plus
fleet-wide aggregates for batch analytics and ML features. The target laptop has 8 GB of RAM.

## Options considered
| Option | For | Against |
|---|---|---|
| **ClickHouse** | Columnar compression; vectorised scans; `ReplacingMergeTree` collapses replays; TTL tiering; **native Kafka engine** (no sink service) | A second SQL dialect; eventual deduplication (needs `FINAL` for exact reads) |
| TimescaleDB | Same engine as the relational store; familiar SQL | Row-oriented inserts; less scan and ingest headroom per core |
| Cassandra | Linear write scaling | Poor ad-hoc analytics; the model must follow the query |

## Decision
ClickHouse 25.8:
- `events` is a `ReplacingMergeTree(ingest_ts)`, ordered by `(tenant_id, vehicle_id, event_ts, seq)`,
  partitioned daily, with a 30-day TTL.
- `vehicle_minute` is a duplicate-safe `AggregatingMergeTree` rollup kept for 400 days.
- Kafka-engine tables with materialised views consume `telemetry.canonical` and `alerts` directly.
  Unparseable messages land in `ingestion_errors` instead of being dropped.

## Consequences
- Measured: 1,772,080 canonical events ingested with **0 ingestion errors** and
  unique `event_id`s equal to the canonical message count
  (`evidence/benchmarks/m6-reconciliation.json`).
- Exact reads before a background merge need `FINAL` or `uniqExact(event_id)`. This is documented
  in `docs/database/data-model.md` and tested.
- CAP: asynchronous replication, so AP/EL. See ADR-004.
