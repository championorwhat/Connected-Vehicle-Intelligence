# ADR-009: Observability: metrics and SLO alerts first, structured logs for correlation, tracing deferred

**Status:** Accepted (M11).

## Context
Prognos runs about 10 processes connected by Kafka. On an 8 GB laptop, every extra
container competes with the data plane for memory. The questions operators need
answered are:

1. Is the product meeting its promises: alerts within 5 s, the API up, fresh data?
2. If not, which stage is to blame?
3. For one failed request, what happened?

## Decision
1. **Metrics (Prometheus) are the primary signal.**
   - Every service exposes `/metrics`, and Prometheus finds replicas by Docker DNS.
   - Service-level indicators are recording rules. Alerts are SLO burn-rate alerts
     (page or ticket), not dozens of static thresholds.
   - Every alert links to a runbook section. Alert logic is unit-tested with
     `promtool test rules` in CI.
2. **Dashboards are generated from code** (`scripts/gen_dashboards.py`). A unit test
   fails if a panel or rule refers to a metric no service exports, which catches
   renamed metrics before they leave an empty panel or an alert that can never fire.
3. **Logs are structured JSON with correlation ids.**
   - `prognos_common.logs` writes one JSON object per line. The API sets the request id
     for the whole request, so every log line and the `audit_log` row share it. Only
     5xx and slow requests are logged, so log volume stays low.
   - Pipeline events carry a deterministic `event_id` end to end: Kafka →
     ClickHouse → alert `event_seq`.
4. **Distributed tracing (OpenTelemetry) is deferred.** A collector plus Jaeger or
   Tempo costs about 0.5 to 1 GB, and it would mostly show things metrics already show:
   per-stage latency is in the histograms, and per-stage backlog is in the lag gauges.
   It becomes worth it with synchronous fan-out across services, which Prognos does not
   have: stages are decoupled by Kafka. The plan is to add it with the cloud deployment
   (M16), propagating `traceparent` in Kafka headers.

## Options considered
| Option | For | Against |
|---|---|---|
| **Prometheus + Grafana + JSON logs (chosen)** | Low memory; SLOs map directly onto metrics; standard tools | No per-request waterfall across services |
| Full OTel (traces, metrics, logs) + collector | One standard; waterfalls | Adds 0.5–1 GB and a collector to run; little extra insight for a Kafka-decoupled pipeline |
| Loki for logs | Log search in Grafana | Another container; `docker compose logs` + JSON + grep is enough locally |

## Consequences
- An operator can answer questions 1 and 2 from one dashboard and act from the linked
  runbook. Question 3 is answered by grepping the request id across the API logs and
  `audit_log`.
- The `ClickHouse` job uses the server's built-in `/metrics` endpoint, so no exporter
  container is needed. PostgreSQL, Redis and Kafka broker exporters are not deployed
  yet; that is recorded as a known gap in `docs/observability/slo.md`.
