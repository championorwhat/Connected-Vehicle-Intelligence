# ADR-008: Serve the failure model in shadow mode, behind a data gate, with rate-invariant features

**Status:** Accepted (M9). Refines ADR-007.

## Context
ADR-007 accepted the LightGBM model on held-out *simulated* data and said the planner
would switch to it once live scoring existed. M9 built live scoring (`prognos-scorer`):
ClickHouse computes the minute buckets, then the training feature SQL runs on them. A
parity test proves ClickHouse and DuckDB produce the same buckets, features and
predictions.

The first live run exposed a gap that the offline tests could not show.
**failure-7d-v2 put 9% of a 100K fleet above 0.5 after 20 s of traffic**
([evidence](../../../evidence/benchmarks/m9-v2-live-shadow-anomaly.json)). Its DTC
features were counts, and the live fleet reports every 10 s while the training fleet
reported every second. The model was extrapolating. Degradation in training is also
time-compressed (32 to 48×), which is a second, unmeasured shift for the slope features.

## Decisions
1. **Rate-invariant inputs (failure-7d-v3, features v3).**
   - DTC counts become per-event rates, and the raw event count is no longer an input.
   - Verified on a new held-out run in which vehicles report every 10 s: PR-AUC 0.679
     vs 0.478 for the rules, a gain of +0.20 [0.15, 0.25].
2. **Data-sufficiency gate.**
   - A vehicle is scored only with at least 30 events **and** data in at least 45 of the
     60 minutes of the window (`SCORER_MIN_EVENTS`, `SCORER_MIN_MINUTES`).
   - An event count alone was not enough. After 6 minutes of live data, v3 still put 8%
     of the fleet above 0.5. The cause was trend slopes fitted to a few noisy minutes
     ([evidence](../../../evidence/benchmarks/m9-scorer-live.json)).
   - Callers fall back to the rules; a missing score is safer than an extrapolated one.
3. **Shadow deployment.**
   - The scorer runs and publishes scores to Redis and ClickHouse, and the API shows
     them on request (`/v1/vehicles/at-risk?source=model`).
   - The planner (`PLANNER_RISK_SOURCE=rules`) and the default ranking
     (`RISK_SOURCE=rules`) stay on the calibrated rules.
   - Switching is a configuration change, recorded on every work order (`model_version`).
4. **Switch criteria.** Switch after the model's live ranking has been compared with
   work-order outcomes (`fault_confirmed` vs `no_fault_found`) and beats the rules. The
   same metrics used offline apply: PR-AUC and precision at workshop capacity.
5. **Versions are immutable.** v2 existed only on the M9 branch and was never served.
   It is removed, but the evidence of why is kept. v1 (M8) is unchanged.

## Consequences
- The product ships with the model live but not in charge. That is the normal way to
  introduce a model whose training data is simulated.
- The time-compression shift is **NOT YET MEASURED** on live data. Real-time
  degradation takes days, which a demo run cannot show.
