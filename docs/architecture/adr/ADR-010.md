# ADR-010: Tenant isolation in two layers: application filters plus PostgreSQL row-level security

**Status:** Accepted (M12).

## Context
Fleet customers (tenants) share one PostgreSQL database. Since M9, every API query filters
by the caller's tenant, and composite `(id, tenant_id)` foreign keys stop cross-tenant
references. That is one layer. A single missed `WHERE tenant_id = ...` in a future
endpoint would leak another customer's vehicles, alerts or work orders, and code review
is the only thing that would catch it.

## Decision
Add a second layer that the database enforces:

1. **Role and context.** A NOLOGIN role, `prognos_tenant`, has row-level security
   policies on every tenant-owned table: `tenant_id = app_tenant()`, where
   `app_tenant()` reads the session setting `app.tenant_id`. The policies apply to
   reads (`USING`) and writes (`WITH CHECK`).
2. **Every tenant request runs as that role.** The API's `tenant_db` dependency switches
   the pooled connection to `prognos_tenant` with the caller's tenant (`set_config`) before
   any query.
   - The pool's `reset` hook runs `RESET ROLE; RESET app.tenant_id` before a connection
     returns to the pool. `RESET ALL` would not work: it does not reset the role, which
     was verified in M12.
   - A caller with no tenant (platform staff) gets NULL, which matches no row.
3. **Least privilege on the role.**
   - It can read the tables the policies allow, but not `users.password_hash`
     (column grants).
   - It can write only what the API writes: alert acknowledgement columns, work orders,
     erasure requests, and audit entries for its own tenant.
   - It cannot DELETE or TRUNCATE.
4. **Pipeline services are not tenant-scoped.** The sink, planner, scorer and erasure
   worker write for every tenant. They keep the owner role, to which the policies do
   not apply.

## Options considered
| Option | For | Against |
|---|---|---|
| **App filters + RLS for API requests (chosen)** | A forgotten filter returns nothing; the database enforces it; no schema change | One extra round trip per request (the `set_config` call); two roles to reason about |
| App filters only (M9) | Simple | One bug from a cross-tenant leak |
| Database or schema per tenant | Strongest isolation | Migrations × tenants; cross-tenant radar and model training become hard; heavy for 20+ tenants on a laptop |
| RLS on the owner role (`FORCE ROW LEVEL SECURITY`) | Covers pipeline code too | Pipeline jobs legitimately span tenants and would need per-tenant loops or BYPASSRLS anyway |

## Consequences
- Integration tests (`tests/integration/test_row_level_security.py`) run queries
  deliberately *without* a tenant filter. They check that only the caller's rows come
  back, that cross-tenant writes and audit forgery fail, and that a pooled connection
  never leaks a tenant.
- ClickHouse and Redis have no equivalent. The API reads only per-tenant Redis keys
  derived from the verified token, and in ClickHouse only `fleet_signals`, which holds
  no per-tenant rows and has counts withheld. Recorded in the threat model.
- The owner role still bypasses RLS. Pipeline code keeps its explicit tenant keys and
  the composite foreign keys.
