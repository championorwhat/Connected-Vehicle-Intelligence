# ADR-003: PostgreSQL for the relational core (tenants, vehicles, alerts, audit)

**Status:** Accepted (M0), implemented in M2 and M6.

## Context
Ownership, RBAC, subscriptions, work orders, alerts and the audit trail need ACID guarantees,
referential integrity across tenants, and business rules that hold regardless of which service
writes.

## Options considered
| Option | For | Against |
|---|---|---|
| **PostgreSQL 17** | Exclusion constraints, partial unique indexes, composite FKs, JSONB, partitioning, row-level security (M12), rich `EXPLAIN ANALYZE` | Single primary for writes (fine at this volume) |
| MySQL | Ubiquitous | Weaker partial indexes and constraints for our rules |
| Store alerts in ClickHouse only | One store fewer | No transactions or constraints; acknowledging and resolving alerts is a state machine |

## Decision
PostgreSQL in 3NF, with one documented denormalisation (`tenant_id` on child rows, guarded by
composite FKs). Business rules live in the schema. Alerts are written by `prognos-sink` with
`INSERT … ON CONFLICT (tenant_id, fingerprint) DO NOTHING` for opens and a conditional
`UPDATE` for clears, so replays are no-ops. A constraint violation isolates only the offending row.

## Consequences
- Measured: 565 alert rows = 565 unique opened fingerprints after a full pipeline run, with a replay
  test proving idempotency (`tests/integration/test_sink_stores.py`).
- Alert volume stays small (transitions, not telemetry), so one primary is ample; read replicas
  are an M16 option.
